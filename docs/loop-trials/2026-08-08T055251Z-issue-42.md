`LibraryView.delete(_:)` did `deleteBlocked = names` — an overwrite. Since
`.onDelete` calls it once per index in the batch, every blocked row but the
last was dropped from the "File in use" alert. Reproduced at HEAD before
touching anything (`App/Sources/UI/LibraryView.swift:153`), exactly as the
issue described. It is dead code today: no multi-select delete UI exists, so
the `IndexSet` never holds more than one index in practice.

Fixed by accumulating through a new static
`LibraryView.blockedNames(_:adding:)` that preserves first-seen order and drops
repeats. The dedupe is not incidental — two WADs in one batch are commonly held
by the same preset, and plain concatenation would have listed that preset twice
in the alert. Three tests added; the issue's verification command ran unmodified
and passed with 166 tests, 0 failures.

**The test targets a static helper, not `delete(_:)` itself.** `deleteBlocked`
is `@State`, which does not behave reliably outside an installed view
hierarchy, so the mutation cannot be driven from a unit test. Extracting the
pure part and testing that is the idiom this same file already uses for
`filesAppURL(for:)`. Worth knowing that this is a deliberate limit: the tests
prove the aggregation function, and the diff shows `delete(_:)` routing through
it — nothing proves the two are wired together except review.

**The surprise was the environment, not the code.** `mise run bootstrap` — step
one of the verification command — failed immediately: this fresh Orca worktree
inherited a gitignored `Vendor/build/` whose `CMakeCache.txt` files hardcode
the owner's primary checkout path (`/Users/tyler/Documents/doom-ios-2026`), so
CMake refused to configure. That is already trap 2 in
`docs/learnings/worktree-setup-traps.md`, whose documented fix (`rm -rf
Vendor/build`, after confirming nothing under `Vendor` is a symlink into the
primary checkout — it was not) cleared it. No learning file added, because the
fact is already recorded and the protocol forbids rewriting one. Worth noting
for whoever reads the trials in aggregate: that learning's provenance is
*manual* worktree setup, but the per-run agent-loop worktrees hit it too, and
it fails at `bootstrap`, not just `build-engine`. If this keeps costing runs
~4 minutes of rebuild, it is a good candidate for the executable check
`CLAUDE.md` asks for.
