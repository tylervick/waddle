Spec §4's reversible hide, model and service only. PR #138. Clean run: 228
tests green locally on the issue's unmodified verification command, CI green,
CodeRabbit reviewed with zero findings of any severity — not one inline
comment — so the fix phase had nothing to do.

**The seeder already satisfied its half of the definition of done.** The DoD
asks that `seedBundledContentIfNeeded()` treat a hidden bundled row as present.
Its presence check is `wadByFilename(_:bundled:)`, which never looked at
`isHidden`, so that was true the moment the flag existed — zero lines of seeder
logic changed. That is the easy thing to mistake for "nothing to do here", so
the work went into proving it rather than writing it: the issue's mutation
instruction (make the presence check ignore hidden rows, confirm the test
fails, restore, confirm it passes) reproduced all three failure modes at once —
a duplicate `freedoom1.wad` row, a fresh UUID that would orphan
`Documents/Saves/<id>/`, and the row silently unhidden. A comment in the seeder
now pins that invariant to the test name, because the next person to "tidy" that
predicate will have no other signal that the omission is deliberate.

I ran the same mutation discipline on `restore(_:)` unprompted, and it was
worth it: both restore tests *passed* against a stub service that persisted
nothing, because they only assert "the item is back on the shelf" and nothing
was being filtered off the shelf yet. They only became real tests once the
filtering existed. Watching them fail against a no-op `restore` is what
confirmed that.

**Two things a human should look at.**

First, the issue and spec §4 both assert that `deleteWAD` throws
`LibraryError.wadIsBundled` for bundled rows, "pinned by
`testDeleteBundledWADThrowsEvenWhenForced`". Neither exists on `main`.
`LibraryError` has exactly one case, `wadReferencedByLoadouts`, and `deleteWAD`
deletes a bundled row's DB entry (it only skips removing the file). So the DoD
clause "the bundled-delete guard and its test are untouched" is satisfied
vacuously. Nothing here touches `deleteWAD` either way, but the guard the spec
believes is protecting bundled rows is not there, and the re-seed-under-a-fresh-
UUID hazard this issue exists to avoid is still reachable through a plain
delete. Flagged in the PR body; probably its own issue.

Second, this run lost ~6 of its 16 minutes to `docs/learnings/
worktree-setup-traps.md` trap 2. `mise run bootstrap` failed because the Orca
worktree inherited a gitignored `Vendor/build/` whose `CMakeCache.txt` hardcodes
the owner's primary checkout path. The learning already prescribes the fix
(`rm -rf Vendor/build`, confirm it is not a symlink first) and it worked
verbatim. Worth noting for the experiment's sake: that learning is written for
someone *setting up* a worktree by hand, but every automated loop run gets a
fresh Orca worktree and so hits it unavoidably and repeatedly — it is a
per-run tax, not a one-time setup gotcha. CLAUDE.md's rule that a learning
which can be an executable check should become one applies here (a bootstrap
preflight that compares `CMakeCache.txt`'s recorded source dir against `$PWD`
would turn six wasted minutes into an instant, self-explaining refusal), but
writing it was outside this issue's definition of done, so I left it alone.

One trap that did not bite, because the index warned about it first:
`docs/learnings/xcodegen-source-snapshot-hides-new-tests.md`. No new test *file*
was added here — the new cases went into the existing
`App/Tests/LibraryServiceTests.swift` — so the XcodeGen source snapshot was
never stale. Had I put them in a new file without re-running `mise run
generate`, the suite would have reported green while never running them.
