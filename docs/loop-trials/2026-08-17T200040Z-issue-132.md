into `TouchTrackRouter`, a pure value covered by 10 new `WaddleTests` cases.

**The 15-minute cap missed CI by 105 seconds.** This is the headline for
whoever tunes the loop. The wait ended at 920s with CodeRabbit's review landed
(`Review completed`, 0 Major/Critical) but `Build + unit tests` still pending,
so 4.1's cap-exceeded first case applied: `ci_result: timeout`, 4.3 skipped,
snapshot pushed from 4.2. That job then finished **`pass` at 16m45s** — 1005
seconds, against a 900-second cap. `ci_result: timeout` and
`test_proof_first: error` are both correct as records of what this run could
observe, but both understate reality, and they will keep doing so on every
future trial unless the cap moves: this repo's CI does not reliably conclude
inside 15 minutes. `test_proof_first: error` is the expensive part — the
leading signal is lost to a margin of under two minutes, on a run that
otherwise went cleanly, and the first CI run's log is sitting right there with
a real proof in it that the protocol correctly forbids reading after the fact.

**CodeRabbit answered, and the ambiguous string resolved the right way.** The
first poll showed `Review skipped: manual review required for this OSS
repository` — the state *before* the explicit `@coderabbitai review` request
was honoured. Section 4.1 makes that string terminal only when
`<CR_REQUESTED>` is `failed`; here it was `yes`, so polling continued and the
real review landed about 15 minutes later with zero Major/Critical findings.
Treating it as terminal would have thrown away a review the run had just
asked for. That rule earned its keep on this trial.

**The work surfaced a live bug, not just an untested decision.** The issue
framed `nearButton(_:)`'s 20pt cushion as the only thing protecting the
`modern` scheme's drag-to-turn region from near-misses on FIRE/USE/weapon
buttons. It was not protecting it at all: the inline code consulted the
cushion only in the stick branch, so a near-miss on the right side started a
turn track and swung the player's view — the exact hazard
`buttonNearMissMargin`'s own doc comment claims it prevents. The comment and
the code had disagreed since the cushion was written. The issue's mandated
unit cases are only satisfiable with the guard applied on both sides, so the
extraction carries that one-line behaviour change, called out explicitly in
the PR body rather than buried as "pure refactor".

**The issue's verification command names a scheme that has never existed.**
`-scheme WADdle -only-testing:WADdleTests`; `App/project.yml` declares
`Waddle` and `WaddleTests`. Run unmodified it fails with `The project named
"Waddle" does not contain a scheme named "WADdle"` — at HEAD, before any
change. The `App/WADdle.xcodeproj` path resolved only because macOS is
case-insensitive, which is what lets the typo survive a casual reading. Run
with the real casing and otherwise unmodified, it passes.

**Both touch UI tests are red at HEAD**, verified by the stash-and-rerun in
`docs/learnings/ui-tests-are-red-at-head.md`: identical failures with the diff
stashed, both dying on `overlay never installed` — the engine session never
installs the overlay, a step upstream of any routing. The failure text
(`modern-scheme drag-turn never reached the SDL shim`) reads exactly like a
broken router, which is the trap, so it is written up as
`docs/learnings/touch-controls-ui-tests-red-at-head.md`. Deliberately prose
rather than a guard script: a check asserting "these two are red" would
enshrine a broken state.
