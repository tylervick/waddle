`EngineSmokeTests/testEngineBootQuitRelaunchCycle` had been red on `main` since
the PR #177 merge. PR #203 fixes it; the cause is PR #177's first-launch
welcome card, found by bisecting the five-merge window the issue named rather
than reasoning about it — `ed49418` (#173) green in 27 s, `9fa7675` (#177) red
in 99 s.

**The issue's own reasoning ruled out the right suspect for a wrong reason,
and that is the thing worth carrying forward.** It argued the welcome card was
not involved because the test never sets `WADDLE_RESET_STORE` and so "never
sees factory state". But a CI runner's simulator has never launched the app, so
first launch *is* factory state — the card was in the failure's own element
dump the whole time. It also inferred "the session does start" from the
`waitForNonExistence` assertion passing, which on cycle 1 returns immediately;
the test says so in its own comment. Both inferences were plausible, written
down as settled, and wrong. Bisecting cost three runs and settled it.

The mechanism took longer than the bisect. On this phone a 408 pt content width
cannot fit two 200 pt grid columns, so the shelf resolves to one full-width
column and the first tile is 544 pt tall; 184 pt of card above it overruns the
viewport. The row still peeked by ~530 pt — far past `minimumGridPeek`'s 120 —
so every guard the code had said it was fine. What broke was the tap: XCUITest
logged `Synthesize event` with no error and the button's action never ran. Three
things nailed it, and the cheap ones came last, which is the lesson: the app's
own `breadcrumbs.log` has no `session begin` line on a failing run and one on a
passing run, a screenshot three seconds after the tap shows the springboard,
and suppressing the card at HEAD turns the test green. **A tap that synthesizes
cleanly is not a tap that landed** — check whether the action ran before
investigating why its consequence never arrived.

Local reproduction was only affordable because `/Users/tyler/Documents/waddle`
was at the same commit with a built `Vendor/out`; copying it and letting
`Scripts/check-engine-fresh.sh` validate the result honestly turned a ~30-minute
from-scratch engine build into ~10 seconds. The fingerprint is content-based and
path-independent, so this is sound rather than a bypass, and it is what made a
three-point bisect fit inside the work budget.

Two protocol frictions, neither fatal. SSH to GitHub was dead all run
(`communication with agent failed`); the documented HTTPS-via-`gh` fallback in
`docs/learnings/unattended-git-auth-hangs.md` worked on every fetch and push,
including the three `loop-trials` writes. And the issue's verification command
names `App/WADdle.xcodeproj -scheme WADdle`, casing that predates `b7fa556`
("rename the app from WADdle to Waddle"); it fails before building. Ran it
verbatim, recorded the error, then used the corrected form, which is
byte-for-byte what `ui-tests.yml` runs.

CodeRabbit returned one Major finding and it was a good one: the budget's
`welcomeCardFullHeight`/`welcomeCardCompactHeight` constants described only the
default Dynamic Type size, so at accessibility sizes a 184 pt constant would
clear a card more than twice that tall and reintroduce the bug. Round 1 replaced
both constants with `welcomeCardHeight` over three measured rows, measured from
`UIFont` in `ShelfView` the way `heroCaptionHeight` already was, plus two
accessibility-size regression tests. `ShelfHeroLayoutTests` went 19 → 22, all
green, and the UI test stayed green.
