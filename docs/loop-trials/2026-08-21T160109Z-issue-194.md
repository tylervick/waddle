Issue #194: every Renovate pull request contributed the identical bullet
"This PR contains the following updates:" to the TestFlight notes. PR #208.

**Reproduced first, hermetically and then for real.** The suite's own
`make_repo`/`stub_curl`/`print_stubbed` helpers lift cleanly out of
`Scripts/test-whats-to-test.sh` with `sed`, so a scratch script could stand up
two fixture Renovate pull requests with byte-identical bodies in seconds and
show the two identical bullets before a line was changed. That same trick —
`eval`-ing `pr_fetch`/`pr_summary`/`changelog`/`format_groups` out of the
script — then drove the real `build-213..build-214` range against the live
GitHub API and reproduced the tester's screenshot exactly: six consecutive
copies of the boilerplate. After the fix, six named dependency updates, with
the other twenty-odd bullets byte-identical across both runs. Worth knowing
for the next release-notes issue: this script's functions are individually
callable, so you can diff real before/after notes without touching the network
policy or waiting for a build.

**Why the bot-author mechanism, not de-duplication.** The issue offered both.
Skipping the summary for bot authors addresses the cause — a generated body is
not a human explaining a change, so its opener was never the sentence
`pr_summary` was written to find — while de-duplication treats the symptom and
silently drops a second genuine bullet when two humans coincide. The commit
subjects it falls back to are strictly better text: they name the dependency,
which is precisely what six identical bullets could not.

**The thing that nearly went unnoticed.** `FETCH_FALLBACK` feeds a stderr note
reading "pull request summaries unavailable for N of M changes". Counting a
bot as a fallback would have made that note claim an API problem that never
happened — the fetch succeeded and the summary was declined. A bot is
therefore counted in `FETCH_TRIED` but not in `FETCH_FALLBACK`.

**`--print` cannot smoke a historical range.** Build tags are repo-global, so
`prev_tag` returns `build-222` no matter which commit is checked out, and in
this worktree (branched before that tag) the range is empty and the script
correctly refuses with "no changes since build-222". That is why the real
before/after went through `changelog` directly. `ci.yml` smokes `--print` on
the pull request itself, where the range is non-empty.

**Signing/auth.** `git fetch` failed twice with `communication with agent
failed` / `Permission denied (publickey)` — 1Password locked, nobody to unlock
it. `docs/learnings/unattended-git-auth-hangs.md` already covers this exactly,
including the cumulative-`credential.helper` trap, so every push here went
through the documented HTTPS-via-`gh` form. Commits signed normally throughout,
since the loop identity is a plain key file under `ssh-keygen`. No new learning
was warranted: the trap was already written down and the fix is self-documenting
in the script's own comments.
