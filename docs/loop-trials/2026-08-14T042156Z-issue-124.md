Why this issue was selected at all is the part worth a human's attention, and
it is not the obvious answer. It was not that the prerequisites were claimed or
excluded — at selection time #118 and #123 were both OPEN, both `agent:eligible`,
both `size:s`, with no `agent:in-progress` and no linked pull request (there
were no open pull requests on the repository at all). On size ordering alone
either would have beaten a `size:m` issue. The cause is
`Scripts/loop-precheck.sh:236`, whose sort key is
`(0 if "agent:next" in names else 1, rank, number)` — **`agent:next` outranks
size entirely**, exactly as its own comment says it should. Issue 124 carries
`agent:next`; #112, #118, and #123 do not. So the owner's priority steer put
the shelf ahead of the three issues the shelf is defined to consume.

That is a collision between two correct mechanisms, not a bug in either. The
precheck has no notion of dependencies and is not trying to have one; the
sequencing lives in issue prose, and `agent:next` is documented as deliberately
overriding size ordering so the owner can steer. The steer simply landed on the
one issue in the group that cannot go first. The gate in #124's body is what
caught it, and the whole cost was one claimed issue and about three minutes
rather than a degraded half-built shelf — the gate earning its keep on the first
run that tested it.

Concretely for the owner: move `agent:next` off #124 and onto #123 (`size:s`,
independent of everything else, spec §8 item 1), then #118, then #112 — the
spec's own landing order. Issue 124 is now labelled `agent:stuck`, which keeps
the loop from re-picking it; clear that label once all three have landed, at
which point this issue becomes straightforwardly workable as written.
