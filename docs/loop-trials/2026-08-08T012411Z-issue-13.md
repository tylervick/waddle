**`ci_result: timeout` here does not mean CI failed. CI passed.** This is the
field's first real conflation and the thing to know six weeks from now: section
4.1 ends the wait only when `gh pr checks` has a conclusion *and* CodeRabbit has
posted ≥1 review, and 4.1's timeout branch writes `ci_result: timeout` for the
whole wait. `Build + unit tests` went green in 6m8s, well inside the cap. What

limited`** — and reports it as `pass`, so the check-level view looks entirely
healthy while zero review bodies exist. The poller sat at
`pending_checks=0 coderabbit_reviews=0` from t+787s to the t+914s cap. So a
`timeout` in this column can mean CI was fine and only the review was missing,
and `coderabbit_findings_first: none` can mean "nothing was ever measured",
not "nothing was found". `Scripts/loop-report.sh` cannot tell those apart.

Two smaller things:

1. **A self-check on the test caught a bad negative-control.** The first attempt
   to prove cases 6 and 7 had teeth built the weakened variants with `grep -v`
   and the patterns silently failed to match, so one "weakened" variant was
   byte-identical to the fixed script and both variants passed. Reading only the
   `ok -` lines would have banked two cases that tested nothing. Rebuilding the
   variants by line number showed both genuinely go red. A negative control needs
   its own diff checked before its result is believed.

2. The `pwd -P` normalisation in the toplevel test is not cosmetic. `git
   rev-parse --show-toplevel` prints the physical path, and the fixtures live
   under `mktemp -d` → `/var/folders/...`, a symlink to `/private/var/...`.
   Comparing against a logical path would make every checkout look misplaced and
   re-clone on every run. Case 3's sentinel file is what would catch that.
