Reproduced immediately and exactly as issue 46 described: `ImportService.swift`
contained no `Task.isCancelled` anywhere, so the three `Task.detached` sites
(hashing at 295 and 312, the disk copy at 377) ran regardless of what the
awaiting task did. The fix is one `guard !Task.isCancelled else { return outcome }`
at the top of the `candidates` loop, matching the idiom already used in
`TitleArtView.swift:84` and `ImportNotices.swift:23`.

The test earned a real `proved`. It was watched failing first — at HEAD the
cancelled scan returned `imported: ["cancelled-DE08DF74-…"]` instead of an
empty outcome, i.e. it had adopted the file, deleted the loose original, and
written to the store despite cancellation. The determinism the issue asked for
came free from actor inheritance rather than from any sleeping or polling: an
unstructured `Task { }` created inside the `@MainActor` test body is enqueued on
the MainActor the test already occupies, so it cannot start until the test
suspends at `await` — cancelling on the very next line is therefore guaranteed
to land before the first candidate is touched. Expected outcome is exactly
empty, never "empty or partial".

**The surprise was the environment, not the code.** `mise run bootstrap` failed
because Orca's fresh worktree inherited a copied, gitignored `Vendor/build/`
whose `CMakeCache.txt` files hardcode the owner's primary checkout path
(`/Users/tyler/Documents/doom-ios-2026`). That is trap 2 in
`docs/learnings/worktree-setup-traps.md`, already written down and already
carrying the exact fix (`rm -rf Vendor/build`, confirm it is not a symlink
first, rebuild) — so no new learning is owed. Worth flagging for whoever tunes
the loop: this costs every fresh worktree a full SDL + OpenAL + Woof rebuild,
about 140 seconds here, and it will recur on every run until worktree creation
stops copying `Vendor/build` or clears it on arrival.

I briefly misread that failure as a mise defect, because the first bootstrap
looked like it exited 0 while printing `ERROR task failed`. It did not: I had
written `mise run bootstrap 2>&1 | tail -25`, so the status I saw was `tail`'s.
That is `masked-exit-status-fails-open.md` — the repo's most-repeated trap —
showing up in an agent's own shell rather than in a guard script. Nothing was
committed on the strength of the wrong reading, but it is a good reminder that
the trap generalises past `Scripts/`.
