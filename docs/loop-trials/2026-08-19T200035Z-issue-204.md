PR #205. The shelf's adaptive grid resolved to one full-width tile per row on
**every** iPhone the deployment target admits, not just narrow ones, so the
first tile row was 3:4 of the whole content width and its bottom sat past the
fold. Standard `Theme.gridMinimumTileWidth` floor 200 → 150, plus a named
`ShelfHeroLayout.minimumFoldClearance` of 44 pt replacing a budget that a row
ending exactly on the fold used to satisfy.

**The base was stale, and that mattered more than usual.** Orca cut this
worktree from `main` at `e9c7e67` — three commits behind, missing PR #203,
which is the change this issue exists to finish. Working on that base would
have meant re-deriving a welcome-card budget that already existed. Fast-forwarded
to `origin/main` (`9584cf2`) before touching anything. Worth checking `git
rev-list --count HEAD..origin/main` at the start of any run whose issue cites a
PR that merged the same day.

**Two facts the issue got wrong, both of which changed the answer.** First, the
narrowest supported iPhone is **360 pt** (12/13 mini), not the 375 pt SE — the
issue asked to "determine the narrowest iPhone width that target actually
admits" rather than assuming 440, which was the right instinct, and enumerating
the iOS 26 runtime's `supportedDeviceTypes` against the CoreSimulator profiles
is what answers it. Second, the issue's measurement table reads "iPhone 17 Pro
(440 × 956 pt)": the 17 Pro is 402 × 874, and 440 × 956 is the 17 Pro **Max**.
The table pairs one device's width with the other's height, which is how it
computed a −30 pt slack for a viewport no user has. The diagnosis survived
intact — every supported width was one column — but the per-device arithmetic
had to be redone.

**The floor is 150 and not the obvious 156.** 156 is exactly `(360 − 32 − 16)/2`
and lands the adaptive fit on precisely 2.0 columns. Choosing it would have
repeated, one dimension over, the same "satisfied by an exact boundary" defect
that made PR #203 flaky. Usable window is roughly 126–156.

**The tests were proved to discriminate**, per the issue's explicit instruction:
floor reverted to 200 turns nine of them red; `minimumFoldClearance` set to 0
turns `testAZoneThatOnlyJustFitsIsRejected` red. Restored, green both times. One
first draft asserted on the exact boundary (`budget == card + clearance`) and
failed — a tile row is 261.33 pt at the reference width, which no binary float
holds exactly. Sit a point either side, not on it.

**Verification.** `WaddleTests` 366/366 on iPhone 17 Pro and again on iPad Pro
13-inch (M4). `EngineSmokeTests/testEngineBootQuitRelaunchCycle` passed three
consecutive times locally, each from a genuine factory-state install
(`simctl uninstall` between runs — the test taps a shelf tile, so it only means
anything on a first launch). The `ui-tests.yml` dispatch against this branch
(run `32298002920`) came back **green**, which is the pre-merge signal the issue
called load-bearing and the thing PR #203 never had.
