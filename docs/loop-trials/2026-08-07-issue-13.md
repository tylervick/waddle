Reason: dry run. This run was invoked with explicit instructions to exercise the
protocol's mechanics only — no code change, no pull request. Issue #13 was never
investigated, so `no-repro` here is a harness placeholder, **not** a finding
about the issue. #13 remains untouched and eligible.

Section 1 behaved correctly: `Scripts/loop-precheck.sh` passed the engine-freshness
check and selected #13 (lowest-numbered `size:xs` with no linked PR).

Three things would have killed a real unattended run, all before any code was
touched:

1. **`agent:in-progress` did not exist as a repo label.** Section 2's
   `gh issue edit --add-label agent:in-progress` fails outright on a missing
   label, so the claim never lands. Worse, `loop-precheck.sh` keys its entire
   liveness and stale-sweep logic on that label, so with no issue able to carry
   it, the "one run at a time" guard is a no-op — two concurrent runs would both
   pass the precheck and could select the same issue. That is the exact
   collision the precheck exists to prevent, and there were two loop worktrees
   live on this machine at the time. The label was created during this run to
   get past the claim.

2. **`agent:stuck` does not exist either**, and the repo already carries
   `agent:blocked` ("Needs a human; reason stated in the issue") for what reads
   like the same role. Section 4 requires `agent:stuck` on every non-`pr-opened`
   outcome, so every unhappy path fails at cleanup. Reconciling the two names is
   a call for the owner; this run did not create it, and did not label #13,
   because `loop-precheck.sh` skips `agent:stuck` issues permanently and a dry
   run should not evict a good issue from the backlog.

3. **Section 0's signing setup cannot produce a commit on this machine.** The
   user's global config sets `gpg.ssh.program` to 1Password's `op-ssh-sign`,
   which only signs with keys held in the 1Password agent. Section 0 points
   `user.signingkey` at `~/.ssh/waddle-agent-signing`, a plain file, and never
   overrides `gpg.ssh.program`; op-ssh-sign rejects it with "invalid ssh public
   key". Combined with `commit.gpgsign true` that is a hard `fatal: failed to
   write commit object` — every loop commit dies, after the issue is already
   claimed. Section 0 needs `git config gpg.ssh.program ssh-keygen` and should
   point at the `.pub`, which is the conventional value. This run committed with
   those two settings supplied inline.

A fourth, quieter one: section 0 uses plain `git config`, but `extensions.worktreeConfig`
is unset in this repo, so those writes land in the shared `.git/config` and
retag the owner's own main checkout with the agent's identity, signing key, and
`commit.gpgsign`. It is a worktree-local intent expressed with a repo-global
command. This run used `git -c` overrides per command instead, leaving the
owner's config untouched.

splits on `': *'` and takes `$2`, so any value containing a colon is truncated —
`timestamp` and `run_id` both are. Harmless today, since the report only reads
`issue`, `outcome`, `prompt_sha`, and `pr`.
