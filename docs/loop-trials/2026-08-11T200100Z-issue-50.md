**The one thing that cost time, and it is already a documented trap.**
`mise run bootstrap` failed within 400ms on
`CMake Error: The current CMakeCache.txt directory .../Vendor/build/SDL-iphoneos
is different than the directory /Users/tyler/Documents/doom-ios-2026/Vendor/build/SDL-iphoneos
where CMakeCache.txt was created`. This is exactly Trap 2 in
`docs/learnings/worktree-setup-traps.md`: a fresh worktree inherits a
gitignored `Vendor/build/` whose CMake caches hardcode the primary checkout's
absolute path. The documented fix — confirm it is not a symlink, then
`rm -rf Vendor/build` and rebuild — worked first try, so no new learning file
was added; the existing one already covers it.

Two details a future run may want. First, the learning describes worktree
setup as *symlinking* `Vendor`, but in this Orca-created worktree `Vendor`,
`Vendor/build`, and `Vendor/build/SDL-iphoneos` were all real copied
directories (verified with `-L` and `pwd -P` before deleting anything —
worth doing, since deleting a symlinked `Vendor/build` would have destroyed
the owner's build tree). The trap is the same either way; only the mechanism
that produces it differs. Second, this failure is easy to misread as a
regression from your own diff, because it surfaces as a bootstrap failure
during verification rather than as anything resembling a Swift error. It is
infrastructure, not the change.

A harness detail also worth flagging: running the verification as
`{ bootstrap && xcodebuild ...; } > log 2>&1; echo "EXIT=$?"` reports the
exit status of the `echo`, not of the build — the completion notification
said "exit code 0" while the real result was `VERIFY_EXIT=1`. The failure was
only visible in the log. Same shape as
`docs/learnings/masked-exit-status-fails-open.md`: read the log, not the
wrapper's status.
