Reproduced cleanly at HEAD by reading the code the issue cites: `touchesBegan`
claims any touch with `point.x < bounds.width * 0.4` as a stick touch with no
button exclusion, and `weaponPrevButton` is placed at `x: minX + inset.left +
40` — inside that same column. The fix skips stick capture for a point inside a
*visible* button's frame grown by 20pt. Hidden buttons are excluded on purpose:
MAP is hidden while a menu is on screen and takes no touches, so the space it
vacates should behave like ordinary overlay.

The interesting part was not the fix, it was making the bug observable at all.
A tap's stick track is created and torn down in milliseconds, so nothing an
XCUITest can query is ever "on" mid-tap, and the shim's touch-event counter
can't distinguish a stick track from any other input. Added a latching
`stickEngaged` marker — the same corner-marker pattern as the existing
`softKeyboardActive` — that flips visible the first time a track engages and
stays visible. The test taps 34pt below the button's center (clear of the 48pt
frame, same x, still in the stick column) and asserts the marker never appears,
then taps clean overlay in the same column and requires it to appear. That
second half matters: without it, a marker that never latched at all would make
the real assertion pass for the wrong reason.

Verified red-green by hand, since the test was written after the fix: reverting
just `&& !nearButton(point)` makes the case fail on exactly the intended
assertion, and restoring it makes the full suite pass.

`test_proof_first: no-test` is honest and expected here, not a defect in the
change. CI runs `-only-testing:WADdleTests`, and this issue's own stated
verification command runs `WADdleUITests/TouchControlsTests` — so the test that
proves this fix is invisible to `check-red-green.sh` by construction. Anything
touching only the touch overlay's UIKit layer will read the same way. Worth
knowing before someone reads a run of `no-test` results as the loop producing
unproven work.

One environmental trap, already documented: `mise run bootstrap` failed
immediately with a CMake source-mismatch error, because this per-run worktree
inherited a *copied* (not symlinked) `Vendor/build` whose `CMakeCache.txt` has
the owner's main checkout path baked in. That is trap 2 in
`docs/learnings/worktree-setup-traps.md`; `rm -rf Vendor/build` plus a rebuild
cost 106s and no new learning was warranted. Note it exits 1 properly — a
compound command of mine ending in `echo` briefly made it look like it had
exited 0, which would have been a much more interesting bug than it was.
