PR #163 applies spec §5's visual system to the shell: four semantic colorsets
(near-black background, one elevated surface, one red accent, warm gray
secondary text), 3:4 tiles with the title on a bottom scrim and one shared
corner radius, a flat surface tile as the no-art fallback, Dynamic Type that
drops grid columns instead of shrinking text, 44 pt targets, and
"DOOM II, last played yesterday" VoiceOver labels.

**The issue's sequencing note was already satisfied.** #125 was written
`agent:blocked` because it styles the shelf from #124, and theming the old
two-tab shell would have been discarded work. #124 had merged by the time the
precheck handed this over, so the shelf was on `main` and there was nothing to
wait for — worth noting only because the note is still in the issue body and
reads, out of context, like a live blocker.

**Two traps, both already written down, both cost real time anyway.** First,
`git fetch` failed twice with `communication with agent failed` — 1Password
locked, exactly what `docs/learnings/unattended-git-auth-hangs.md` describes.
The HTTPS-via-`gh` fallback with the `credential.helper=` reset worked on the
first try, and every push in this run used it. Second, `mise run bootstrap`
died immediately on a `CMakeCache.txt` pointing at
`/Users/tyler/Documents/doom-ios-2026` — trap 2 of
`docs/learnings/worktree-setup-traps.md`. Neither `Vendor` nor `Vendor/build`
was a symlink here, so `rm -rf Vendor/build` was safe, and the full SDL + Woof
rebuild that followed took ~95 s of wall clock but the confirming check cost
more than the fix did. Nothing new to add to `docs/learnings/` — both files
already say precisely what to do, which is the system working. The observation
worth passing on is that an Orca per-run worktree arrives with a *copied*
`Vendor/`, not a symlinked one, so trap 2 fires on essentially every run that
needs a build, and the "confirm first that it is not a symlink" step in that
learning is the part that keeps costing a round trip.

**On the tests.** The repo has no view harness, so the two rules the issue
names are pure functions and the views read *through* them:
`TileAppearance.resolve` decides art vs. the flat fallback and `TitleArtView`
takes its image from that decision rather than testing its own `@State`
directly, so the drawn result cannot drift from the tested rule. The
discrimination proof the issue asked for behaved exactly as intended — making
`resolve` return `.art` for a nil image failed
`testItemWithNoDecodableArtResolvesToFlatTitledFallback` ("art" is not equal to
"flatTitle") and *only* that test, out of 280.

`TileAccessibility.label` takes a `locale` parameter defaulting to
`.autoupdatingCurrent`. That exists so the test can pin `en_US` and assert the
spec's own example string verbatim instead of asserting a shape like
`hasPrefix("DOOM II, last played ")` — the weaker form would have passed for
any relative-date phrasing at all, including none.

**`test_proof_first: proved-by-compile`, not `proved`.** Worth reading
honestly: the new tests are real and discriminating, but the change is
overwhelmingly SwiftUI view code that no test in this repo can observe. The

verified by compiling and by the owner's eye on the PR, which the issue
explicitly reserves as the final judgement. A future reader should not read
this trial as evidence that the *visual* system is proven.
