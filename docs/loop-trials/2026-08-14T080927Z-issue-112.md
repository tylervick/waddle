Issue #112: give a playable item with saves a one-tap Continue that boots the
engine straight into its newest save via `-loadgame`. PR #142. CI green,
verification green, no fix rounds — CodeRabbit reported `Review rate limited`
as a *check status* rather than a review, so `coderabbit_findings_first` is
`unavailable` and the fix phase was skipped by design, not by timeout.

**Reproduction was trivial and worth stating:** `grep -rn loadgame App/` at HEAD
returns nothing but a mention in a design spec. The flag was never passed, full
stop.

**The interesting part was reading the engine, not writing the app.** The naive
shape of this feature — "list the `.dsg` files, take the newest, pass its number
to `-loadgame`" — is wrong twice, and the second way fails on the *common* case:

1. The argument is the composite `10 * page + slot` (0–77) that the filename
   itself carries, not a slot index. And the filename prefix is `woofsav`, not
   the `doomsav` every DOOM-lineage reference predicts, because it derives from
   `PROJECT_SHORTNAME` via `"%.4ssav"` and this project pins that to `woof`.
2. The autosave is a *separate* sentinel — 255 — under the fixed name
   `autosave.dsg`. And `autosave` defaults to **on**, saving at every level
   start, so `autosave.dsg` is routinely the newest file in a real saves
   directory. Code that assumes every save name carries a parseable number would
   have skipped the newest file on the default path, not on an edge case. That
   the predecessor's RESUME GAME also preferred the live level over the last
   manual save makes resuming it the right behaviour as well as the necessary
   one.

Both are now in `EngineSaveSlot` with the four Woof source sites cited inline,
plus a learning file, because the next change here (#121's Continue hero) will
need exactly this and would otherwise re-derive it.

**One environment trap, already documented, cost about eight minutes.**
`mise run bootstrap` failed immediately: this worktree inherited a gitignored
`Vendor/build` whose `CMakeCache.txt` files hardcode the *primary* checkout's
path. That is trap 2 in `docs/learnings/worktree-setup-traps.md` verbatim — the
fix (`rm -rf Vendor/build`, rebuild) worked first time, but the rebuild of SDL +
OpenAL + Woof from a cold cache is ~100s of CMake plus compile time. Worth
knowing that a per-run worktree pays this on every first bootstrap: the sources
in `Vendor/src` and the built `Vendor/out/WoofEngine.xcframework` come across
fine, only the build directory is poisoned. An executable check that refuses a
`Vendor/build` whose cache path is not this checkout would turn eight confusing
minutes into one clear error, and is probably worth filing.

**`test_proof_first` came back `proved-by-compile`, not `proved`.** Recording it
as measured and deliberately not chasing it, per section 4.1. Reading it at face
value: the red-green harness reverts the diff and expects the suite to go red,
and a revert that deletes a brand-new type (`EngineSaveSlot`) plus the new tests
that reference it breaks the *compile* rather than producing a clean assertion
failure. That is the expected shape for a change whose tests are the first
consumer of a new type, and it is not the same signal as a vacuous test — the
discrimination proof the issue asked for was run by hand and is unambiguous:
flipping the newest-first comparator to oldest-first turned the suite red
(`** TEST FAILED **`, exit 65, 7 assertions across 6 tests, including both the
several-saves selection and the autosave-is-newest case), and restoring it
returned 259 green. A human reading this in six weeks should not read
`proved-by-compile` here as a weaker result than `proved`; if that distinction
matters for the experiment, the harness — not this diff — is where it gets
sharpened.
