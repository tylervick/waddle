PR #153. A docs-only change to
`docs/superpowers/specs/2026-08-11-whats-to-test-design.md`; no script
behaviour changed.

**The issue body and its own comment disagree about scope, and the comment
wins.** Issue 84's definition of done asks for `Scripts/whats-to-test.sh` to
end its changelog range at the build's own commit and to refuse for untagged
builds, with new `test-whats-to-test.sh` cases for both. The owner's comment
then downgraded the issue: historical builds are out of scope, "we are only
moving forward", and on the workflow path the `..HEAD` endpoint is *correct*
because the script runs at the commit being shipped. That comment explicitly
says it "removes every documented failure mode in this issue". Implementing
the refusal would have changed release-path behaviour the owner had since
declared correct, and would have contradicted the same comment's defence of
the bootstrap fallback. So the script was left alone and the two surviving
documentation defects were fixed instead. This is the judgement call a human
should check first; it is flagged in the PR body too.

A consequence worth naming: with no behaviour change there is nothing for new
test cases to discriminate against, so the issue's "must gain cases"
requirement could not be honoured as written. The three verification commands
were still run unmodified and all pass; none of the existing 25 cases were
touched or weakened.

**Both defects reproduced at HEAD before being fixed.** (1) The spec claimed
the script is simply "runnable outside the workflow" — true only while `HEAD`
is still the commit the build shipped from, since the range ends at
`$TAG..HEAD` rather than at the build's own commit. (2) The spec's documented
tag recovery, `git tag build-<N> && git push origin build-<N>`, fails on any
machine with `tag.gpgSign = true`. Reproduced directly in a scratch repo:
`git -c tag.gpgSign=true tag build-999` → `fatal: no tag message?` (exit 128),
while the `-c tag.gpgSign=false` form exits 0.

**The surprise was that half of defect (2) was already fixed.**
`.github/workflows/testflight.yml` lines 202-205 already print the corrected
`git -c tag.gpgSign=false tag build-$N` form in its own failure message. Only
the spec still carried the broken command — the document had drifted from the
workflow it describes. That is a no-repro for the half the issue comment was
actually pointing at, and worth knowing for anyone re-reading the comment: the
fix landed in the workflow but nobody propagated it to the spec.

computed it, and there is no code path for a test to prove. CodeRabbit
