stamped `bundled:freedoom1.wad` / `bundled:freedoom2.wad` placeholders into
the rows' `sha1`, and `ImportService`'s hash-first dedupe
(`findWAD(sha1:)`) can never match a real content hash against those. The
red run is the reproduction evidence: with only the tests applied, importing
a byte-identical copy of `freedoom1.wad` produced a third library row and an
empty `duplicates` list, and the seeded rows carried the placeholders where
the real hashes (`97bb8809…`, `975f781e…`) belonged.

The fix is the minimal shape the issue's provenance note already blessed:
hash the bundle resource at the one time the row is created — the existing
`wadByFilename` guard already makes creation once-per-install, so
steady-state launches still never hash the ~30MB files, which is what the
original `bundled:` pseudo-hash design was protecting. Two tests prove it
(row hash = streamed hash of the bundle resource; end-to-end import of a
byte-identical copy reports a duplicate and creates no row). Verified red
