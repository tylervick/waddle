The "File in use" alert pooled every blocked preset name into one list and
closed with "Remove **it** from those presets first." Reproduced at HEAD before
touching anything: `LibraryView.swift:162` really does accumulate across a
delete batch (PR #61 made it so), while `:80` still spoke as if one WAD were
involved.

The interesting part was that this could not be fixed as a copy edit. The
obvious minimal change is "it" → "them", but `deleteBlocked` held only preset
names — it does not record *how many files* are involved, so nothing downstream
can pluralise correctly, and with one WAD held by two presets a count taken off
that array pluralises off the wrong noun entirely. The issue's own complaint
("the reader cannot tell which file to remove from which preset") is a data
problem wearing a copy problem's clothes. So `deleteBlocked` became one
`BlockedFile` per refused file, each keeping its own presets, and
`blockedMessage(for:)` builds a line per file plus a closing sentence that
agrees in number with what is listed.

Deliberately did **not** change `blockedNames` or its two existing tests. It
still does real work — deduplicating preset names within one file's list, since
two loadouts may share a name — so the new `blockedFiles` calls it rather than
replacing it. That kept the rule about never editing an existing test intact
without leaving dead code behind.

`test_proof_first` is `proved-by-compile` rather than `proved`, and the reason
is structural, not a weakness in the tests: the change *adds* API
(`BlockedFile`, `blockedFiles`, `blockedMessage`), so reverting
`App/Sources/UI/LibraryView.swift` leaves the new tests referencing symbols that
do not exist at base and the revert fails at compile time before any assertion
runs. Any change shaped like "add a new function and test it" will land here.
Recorded, not acted on, per section 4.1.
