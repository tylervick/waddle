PR #162 adds `BreadcrumbLog`: a small, launch-spanning app-event trail written
beside the engine session logs and bundled by the same export. It exists
because the session logs stop at whatever the engine last printed, which is
the wrong place when the app is stuck *after* the engine exited — issue #95's
non-dismissable alert needed a force quit and left no trace, and MetricKit
stayed silent because the main thread was never blocked. An "alert presented"
line with no matching "alert dismissed" before the next "app launch" is that
evidence.

Verification (`mise run bootstrap`, then the issue's `-only-testing:WADdleTests`
command unmodified) passed both times it was run: 285 tests before the fix
round, 288 after, 0 failures. CI passed on both pushes.

**What surprised me — the review found a real privacy hole in the redactor,
and it was the interesting kind.** The sanitizer reduced each
whitespace-separated token to its last path component. CodeRabbit pointed out
that a *space inside a directory name* defeats that entirely: `Failed to load
/Users/Alice Smith/My WADs/private.wad` tokenizes as `/Users/Alice` +
`Smith/My` + `WADs/private.wad`, and `Alice` — a home-folder name — survives
as a bare word. The fix reduces the whole *run* of separator-carrying tokens
together, so everything ahead of the span's last separator is dropped, and
keeps the final component only when it reads as a file name (a path can end in
a directory just as easily; that case is ambiguous and gets redacted whole).
Worth noting for anyone writing a redactor here: tokenize-then-redact is
backwards, because tokenization is exactly what the adversarial input attacks.
This is a simulator-real path, not a hypothetical — macOS home directories
routinely contain a space.
