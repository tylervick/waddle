PR #207 caps the first-launch welcome card against the measured viewport in
`ShelfHeroLayout`, mirroring the Continue hero's existing `sectionSpacing` +
`minimumGridPeek` arithmetic. Eight new hermetic cases; all 19
`ShelfHeroLayoutTests` pass, and the unit suite is green on both destinations
(347 tests each).

**The issue's diagnosis is wrong, and that is the most useful thing here.** #183
says the card pushes the shelf's first tile row out of reach on a landscape
phone, breaking
`PlayTabTests/testBaseGameDetailControlsOverridePersists`. Measured from
`UIFont` at test time, the card is 165.3 pt at the default type size against
~231 pt of room on a landscape phone — it already fit, with 185.7 pt of grid
band. And `ui-tests.yml` runs on an iPhone 17 Pro in *portrait* (~744 pt
viewport), where the card takes 183.2 pt and leaves ~537 pt. The card was never
within ~350 pt of causing that failure. I then confirmed it experimentally: that
test still fails **with the fix applied**, at the same `PlayTabTests.swift:18`
"No matches found" for the context menu's Details item.
`docs/learnings/ui-tests-are-red-at-head.md` already records that exact test as
red at HEAD since 2026-08-16 — before PR #177 introduced the card. The issue's
own isolation table uses `PresetEditTests` as its passing control, and that
learning lists it as red too.

So the definition of done is **partly unmet**: the named UI test does not pass,
and `verification_result` is `fail` for that reason. What the change does fix is
real but different — an accessibility-type-size defect. At AX5 the card's three
rows come to 319.4 pt, which left 31.6 pt of grid band, under both the 120 pt
peek and the 44 pt tap target. Remove the ceiling and the new case fails on both
assertions; restore it and the band is 120 pt. That discrimination was proven by
actually removing the cap and re-running, as the issue required.

**A valid Major finding is outstanding and unaddressed.** CodeRabbit is right
that `.frame(maxHeight:)` only *proposes* a height, and the explanatory line's
`.fixedSize(horizontal: false, vertical: true)` makes it ignore that proposal —
so at AX sizes the card overdraws the grid row instead of shrinking. The fix
reserves the correct layout space (so the row is instantiated and hittable —
the accessibility half of the defect), but does not prevent visual overlap. This
run reached 4.1's cap with the review landed and no CI run ever created, which
routes to `ci_result: timeout` and skips 4.3, so I left the code alone and wrote
the analysis into a PR comment instead. This is precisely the containment hole
the protocol's Known Gaps section describes; the PR needs the owner.

**Two environment traps cost roughly nine minutes.** First, an Orca worktree
inherits the gitignored `Vendor/build/` from the primary checkout with every
`CMakeCache.txt` hardcoding that checkout's path, so the first `mise run
bootstrap` fails — already documented as trap 2 in
`worktree-setup-traps.md`, and `rm -rf Vendor/build` fixed it. Second, and new:
killing an `xcodebuild` UI-test session wedges CoreSimulator so every later
launch fails with `Busy ("Application failed preflight checks")`, which surfaces
as ordinary per-test failures pointing at `app.launch()` in your own test file.
Four unrelated classes went red across two runs and read exactly like a
regression in the diff. `simctl shutdown all` does not clear it; the
`CoreSimulatorService` must be restarted, and the simulators pre-booted with
`simctl bootstatus` to avoid racing a cold boot. Written up as
`docs/learnings/killed-xcodebuild-wedges-coresimulator.md`. I caused that wedge
myself by killing runs to re-freeze the tree — the lesson is to stop editing
before starting the authoritative run, not to kill it afterwards.
