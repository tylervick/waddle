**`test_proof_first: vacuous` is structural here, not sloppiness, and a future
reader should not "fix" it.** The change is a memory-behaviour change with
deliberately identical observable results — `Data` indexes a mapping exactly
as it indexes a heap buffer, so parse, family detection, SHA-1 and dedupe all
produce the same values before and after. No honest test can go red on the old
code, because the old code is not wrong about *results*; it is wrong about
residency. The issue anticipated this and explicitly forbids asserting peak
memory (`XCTMemoryMetric` on a simulator does not measure what a device's
jetsam limit cares about, and a flaky gate there would be worse than none).
The three tests added are equivalence guards — mapped vs plain reads agree
byte-for-byte, and both import paths hash a mapped WAD to its on-disk SHA-1 —
which is the right shape for this change and still scores `vacuous`. Per
section 4.1 the verdict was recorded and not acted on. If the red-green
measurement is ever refined, "correct-by-construction API swaps" is the
category this run belongs to.
