Issue #169: long-press → Details on a shelf tile "never opened the detail
sheet". PR #178, CI green, CodeRabbit approved with no findings.

**The issue's suspected cause was wrong, and the issue said so itself.** It
named a SwiftUI context-menu dismissal race — `ShelfView` already carries a
comment about that exact hazard for the *editor* sheet — but flagged it as
"the first place to look, not a conclusion". That hedge was worth its weight.
The sheet was presenting correctly every single time. `PlayableDetailView`'s
header art was drawn at `Theme.tileAspectRatio`, a portrait *tile* shape, which
at a sheet's full width came out 481 pt tall in a 708 pt viewport. A SwiftUI
`Form` is a lazy collection view, so `detailSchemePicker` and `detailEditButton`
were never instantiated — not merely off-screen, but absent from the
accessibility hierarchy, which is indistinguishable from a screen that never
appeared if you only read the assertion message.

**What settled it in one read, and cost nothing:** the failing run's own result
bundle. `xcrun xcresulttool export attachments` yields an "App UI hierarchy"
text file — the full element tree with frames, captured at the moment of
failure. It showed the sheet's navigation bar, its art, its title and
`detailPlayButton` all present, and the rows below them simply absent. The
plain xcodebuild log carries a weaker version of the same evidence for free:
the `from input {( ... )}` list in the failure message already had
`detailPlayButton` in it. I had spent a while before that reading git history
to work out which commit introduced a presentation race, which was time spent
on a theory the evidence never supported. That is the learning added here.

The fix mirrors `ShelfHeroLayout`, which had already been written for this
identical defect one screen over — a `LazyVGrid` hiding the whole library
behind an oversized hero. `PlayableDetailLayout` is its sibling: pure geometry,
tested over supplied bounds, capping the art against the measured viewport so a
short viewport (landscape, which this app supports) shrinks the art rather than
the controls.

**Environment trap, already documented and still expensive:** `mise run
bootstrap` failed immediately because this fresh Orca worktree inherited a
gitignored `Vendor/build/` whose `CMakeCache.txt` hardcodes the *primary*
checkout's path. `docs/learnings/worktree-setup-traps.md` names this exactly
(trap 2) and the fix is `rm -rf Vendor/build`; the rebuild then took 96
seconds, not the many minutes I had budgeted for. Worth knowing that this
failure is cheap to clear, because its error text looks alarming.

**A hazard in my own tooling, not the repo's:** I ran the first bootstrap as
`mise run bootstrap > log 2>&1; echo "EXIT:$?"`, and the trailing `echo` made
the whole command exit 0. The harness reported success for a command that had
failed, and I only caught it because the *next* step could not find the
`.xcodeproj`. Do not append an `echo` to a command whose exit status you intend
to read.

`docs/learnings/ui-tests-are-red-at-head.md` ends with "if these two go green,
delete this file rather than working around it" — they are green now, so it is
stale, but the loop protocol forbids an agent deleting a learnings file. That
is a genuine standoff between a learning's own instruction and the guardrails,
and it needs a human hand. Second, the shelf context menu's `Edit` shortcut and
the tap-with-saves action sheet's `Details` are both entirely untested; neither
is touched by this change, but nothing proves either works, and the issue's

than a test.
