Stuck for a reason that has nothing to do with the clock: **the issue's
definition of done requires editing two files this protocol forbids the loop
from touching.** #68 asks for a change to `Scripts/loop-report.sh`'s legacy
live-query branch, and states that `Scripts/test-loop-report.sh` "must gain a
case for the failed-query path." Both files are named in section 7's
never-modify list — the entry that adds "the last two are the tests of your own
guardrails. Those are the rules you are judged by." There is no reading of that
rule under which an unattended run edits its own report and its own report's
tests, and the fact that a backlog issue *asked* is not an exception; if it
were, the rule would protect nothing, since the way to get an agent to edit its
guardrails is to file an issue asking it to.

So this is not `no-repro` and not `failed-verification`. The bug is real and I
never got to attempt a fix. `stuck` is the only honest slot in the closed
vocabulary, but "ran out of time" — the gloss section 3 gives it — is the wrong
picture. It stopped at 328 seconds with 40+ minutes of budget unspent.

**The defect reproduces exactly as described.** `Scripts/loop-report.sh:232-235`
still has the pre-PR-#66 shape, `gh api ... 2>/dev/null | grep -c -E "$MARKERS"
|| true`. I demonstrated it hermetically rather than reasoning about it: one
fixture record with `coderabbit_findings_first` absent entirely (so it takes the
legacy branch), scored twice with different stub `gh` binaries on PATH —

- stub that exits 1 on every call, printing to stderr: `0 CodeRabbit
  Major/Critical across 1 PR(s)`
- stub that exits 0 and returns no matching bodies (healthy API, genuinely
  clean review): `0 CodeRabbit Major/Critical across 1 PR(s)`

Byte-identical, including the legacy caveat line. A reader of that output cannot
distinguish "queried GitHub, CodeRabbit found nothing" from "never reached
GitHub at all." That is the same fabrication PR #66 removed from the
reconciliation path, which is exactly what the issue claims.

Baseline is green and untouched, so whoever picks this up starts from a clean
floor: `Scripts/test-loop-report.sh` (all cases), `Scripts/test-loop-precheck.sh`,
and `Scripts/check-substrate.sh` all pass at HEAD, and `git status --porcelain`
is empty — the whole reproduction lived in a scratch directory. `verification_result`
is `not-run` rather than `pass` on purpose: the suite passing against an unchanged
tree says nothing about a fix that was never written, and `pass` would read as
though it did.

**The part worth a human's attention is not #68 itself — it is that #68 was
labeled `agent:eligible` at all.** `Scripts/loop-precheck.sh` selects purely on
labels (`agent:eligible`, not `agent:stuck`, no linked open PR, size rank, then
issue number). Nothing anywhere compares an issue's definition of done against
the never-modify list, so an issue that cannot lawfully be completed by the loop
is indistinguishable from any other `size:xs` bug at selection time. It wins the
tie-break like anything else, consumes a real run's claim, and the run can only
discover the conflict after reading the body. This one is now `agent:stuck` so
the precheck skips it, but the class recurs: `Scripts/loop-report.sh`,
`loop-precheck.sh`, and their tests are exactly the files that reviews of loop
PRs generate follow-up findings about, which is precisely how #68 came to exist
(provenance: raised during review of PR #66). Expect more of these.

I deliberately did not open a pull request, not even for a `docs/learnings/`
file. The natural executable check for this — teach `Scripts/check-issue-format.sh`
to refuse `agent:eligible` on an issue whose body names a never-modify path, the
pattern CLAUDE.md prefers over prose — is itself unavailable, because
`check-issue-format.sh` is on that same list. A learnings-only PR on a `stuck`
trial would also put a `pr:` number on a record whose work never happened, which
muddies the one signal this experiment is built to read. The issue comment and
this record are the right channel; both go to the owner, who is the only actor
who can fix either problem.
