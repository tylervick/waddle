Spec §§2–3's shelf, replacing the Play/Library `TabView`: a Continue hero, one
adaptive grid of base games and presets mixed, and two doors (a gear opening a
player-settings sheet, a Manage push holding the library workspace). PR #144.

The issue's sequencing gate was the first thing checked, and all three
prerequisites were already on `main` — #112's `-loadgame`, #118's recognized
titles, #123's `isHidden` — so nothing had to be stubbed.

**The interesting decision was about tests, and it cuts against a rule.** The
issue's Verification section says "do not edit or weaken any existing test".
But the design of record it points at says, in §7, "UI tests re-point to the
shelf" — and it has to, because five UI suites navigated by
`app.tabBars.buttons["Play"]`/`["Library"]`, and this change deletes the tab
bar. There is no honest way to build the spec'd shell and leave those
navigation lines standing: they address a control that no longer exists.
What I did: added two shared helpers (`openManage` / `returnToShelf`) and
changed *only* the route each test takes to reach its screen. Not one
assertion was relaxed, deleted, or skipped. The distinction I worked to is
that "never weaken a test" is about the claim a test makes, and the claims are
all still there and all still checked. A reader six weeks from now who wants
to audit that should diff `App/UITests/` in #144 — it is small and entirely
navigation.

`ShipUITests` is the nicest evidence that the rework is behaviour-preserving:
it taps the gear by its old identifier (`touchSchemeMenu`, deliberately kept
on the new button) and walks into About. It passes completely unedited, even
though the gear went from a `Menu` to a sheet.

**Surprise: CodeRabbit declined to review at all** — its check row read
`Review skipped: manual review required for this OSS repository`, a `pass`
bucket with no review behind it. The protocol names `Review rate limited` as
the observed terminal string; this is a second string in the same class, and
treating it as terminal (rather than polling 900s for a review that had
already declined) is what §4.1's terminal-non-review rule is for. Recorded
`unavailable`, skipped 4.2/4.3. Worth noting for whoever tunes that
detection: matching on the literal `Review rate limited` alone would have
burned the full cap here.

**`test_proof_first: proved-by-compile`, not `proved`.** Reading the change,
that seems right rather than a defect: the new tests are hermetic
value-in/value-out tests over `Shelf` and `LibraryService.shelfItems()`, and
the bulk of the diff is SwiftUI view code the repo has no harness to test. I
did run the red-green discrimination the issue asked for, by hand: inverting
`Shelf.ordered`'s recency comparator fails exactly
`testShelfOrdersRecentlyPlayedFirstThenAlphabetically`
(`["mid","zulu","alpha"]` vs `["zulu","mid","alpha"]`) and nothing else;
restoring it passes. Per §4.1 I did not act on the proof verdict.

Verification was `mise run test`, unmodified. Everything passes except
`RealWADTests`, which needs the provisioned fixture WADs this machine does not
have — expected, per `docs/learnings/simulator-test-hazards.md`, not a
regression. Because that suite spends minutes in 90-second waits before its
expected failure, I confirmed the three suites that run after it
(`ShipUITests`, `SoftKeyboardTests`, `TouchControlsTests`) with a targeted
`-only-testing` invocation instead of sitting through it twice; all three
pass. CI, which runs `-only-testing:WADdleTests`, is green.

The learning added is the one this run actually paid for: `mise run generate`
fails spec validation in a fresh worktree because `App/Resources/GameData` and
`woof.pk3` are gitignored build outputs, and the error reads like a broken
`project.yml` rather than a missing bootstrap step.
