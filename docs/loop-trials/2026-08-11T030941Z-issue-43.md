`testBuildBaseGameOnlyArgv` and `testBuildWithPWADsAndComplevel` passed an
inline `UUID()` straight into `LoadoutArguments.build(iwadURL:saveID:...)`, so
the directory that call unconditionally creates
(`App/Sources/Library/LoadoutArguments.swift:23-24`) had no id the test could
name afterward, and neither test removed it. Fix is the one the issue asked
for and nothing else: hold the id in a local, register the same
`addTeardownBlock` cleanup the two older tests in the file already use.

**Reproduced empirically, not just by reading.** Code inspection was already
conclusive — `build` creates the directory on every call and neither test has
a cleanup path — but it was cheap to prove: with the simulator container's
`Documents/Saves` removed, running only those two tests at HEAD left exactly
2 `Saves/<uuid>` directories, one per test. After the change, the full
`LoadoutArgumentsTests` suite leaves `Saves/` with 0 entries. The issue's
verification command ran unmodified: 6 tests, 0 failures, `** TEST SUCCEEDED **`.

**One measurement trap worth knowing if you ever repeat this.** `xcodebuild`
reinstalls the test host, and the reinstall hands the app a *new* data
container. The first litter count I took was against the container path I had
resolved before the run, which by then was the old one — it read 0 and looked
like a clean bill of health. Re-resolving with `simctl get_app_container`
after the run showed the 2 directories. Any before/after count of simulator
container state has to re-resolve the container path on both sides, or it
silently measures an abandoned directory. The stale containers are still on
disk with their own accumulated litter (one had 5 entries), which is a decent
illustration of why this issue is worth fixing at all.

**The `Vendor/build` trap hit again, exactly as trial 2026-08-08T055251Z

`Vendor/build/` whose CMake caches hardcode the owner's primary checkout path,
and `mise run bootstrap` again could not configure until `rm -rf Vendor/build`
cleared it — about 3 minutes of rebuild. That is trap 2 in
`docs/learnings/worktree-setup-traps.md`; no learning file added, because the
fact is already recorded and the protocol forbids rewriting one. This is now
the second consecutive trial to pay it. The previous trial suggested it as a
candidate for the executable check `CLAUDE.md` asks for; a second occurrence
is decent evidence that suggestion was right, but writing that check is not in
this issue's definition of done, so it stays a note rather than scope creep.
