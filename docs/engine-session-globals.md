# Engine globals that survive from one session to the next

`WoofIOS_Run` runs `D_DoomMain` once per play session, several times in one
process; upstream Woof! assumes one run per process. This is the
classification issue #266 asked for: every engine variable that the
writable-globals diff (`WADDLE_DEBUG_GLOBALS_DIFF`,
`WaddleUITests/GlobalsDiffProbeTests`, `Scripts/globals-diff.py`; see
`Engine/WOOF_UPSTREAM.md`, "Task 10") reported as changed between two
sessions, and what each one means.

## How the lists were taken

Simulator (iPhone 17 Pro, iOS 27.0), 2026-09-23, with the menu-table reset
from #255 in place and none of the resets below. The diff compares the image's
writable data at the start of each session's game loop: after all of
`D_DoomMain`'s init and the first tic (which shows the title page), before the
first frame.

| Run | Games | Autoquit | Result |
|---|---|---|---|
| `12s` | Freedoom Phase 2, Phase 2 | 12 s | 168 engine variables |
| `40s` | Freedoom Phase 2, Phase 2 | 40 s | 442 engine variables |
| `x` | Freedoom Phase 2, Phase 1 | 40 s | 464 engine variables |

How long session 1 runs decides what the list can see. Phase 2's title page
lasts about 11 s, so at 12 s session 1 quits on the title and no level state
enters the list. At 40 s the first demo has loaded a level, which is the run
the issue's 402-variable count came from. `GlobalsDiffProbeTests` now takes
`TEST_RUNNER_WADDLE_GLOBALS_DIFF_AUTOQUIT` so both can be reproduced:

```
TEST_RUNNER_WADDLE_GLOBALS_DIFF_AUTOQUIT=40 \
TEST_RUNNER_WADDLE_GLOBALS_DIFF_GAMES="Freedoom Phase 2,Freedoom Phase 2" \
xcodebuild -project App/Waddle.xcodeproj -scheme Waddle \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:WaddleUITests/GlobalsDiffProbeTests test
Scripts/globals-diff.py --container <udid>
```

The union of the two same-game runs is 446 variables; the cross-game run adds
29 more, listed separately at the end.

## Classes

| Class | Count | Meaning |
|---|---|---|
| harmless | 366 | Rewritten before any read in the next session; the evidence cites the rewrite, or the gate that keeps it from being read until then. Where the rewrite orphans the old allocation, the row says so (#269 tracks the growth). |
| shared | 30 | Deliberately outlives the session: a config-bound value, a cache whose key is still valid, a one-time registration, or the probe's own bookkeeping. |
| reset | 23 | Read before being rewritten; now reset per session under `WOOF_IOS`, with a red/green test (below). |
| follow-up | 56 | Read before being rewritten, confirmed in the code, but the Freedoom-only test cannot make it fail, or it is a leak rather than a stale read. Tracked: #268 (automap, HUD, SDL objects), #269 (the zone's PU_STATIC growth, still open), #270 (DEHACKED). |

## The resets, and the test that proves each

`WoofIOS_DebugSessionStartState()` captures these values at the same point as
the diff; the app shows them after the session (`WADDLE_DEBUG_SESSION_START`).
`WaddleUITests/SessionStartStateTests` plays Phase 1, Phase 2, Phase 2,
Phase 1 (16 s each) and asserts that every session starts from upstream's
values and that the same game starts the same way; a second case plays Phase 2
twice at 8 s, so session 1 quits on the title page. The red runs below had
the resets turned into no-ops and nothing else changed.

| Field | Variable (what leaked) | Reset in | Red run |
|---|---|---|---|
| `exit` | `fast_exit` (`d_main.c`): set by the previous session's `SDL_EVENT_QUIT`, so every later session exited as if the window had been closed | `D_ResetSessionState` | `exit 0 -> 1` |
| `wipe` | `wipegamestate`, `screen_wipe_internal` (`d_main.c`): a session after a quit mid-demo started with a screen wipe into its title page (`d_main.c:265`), which session 1 does not | `D_ResetSessionState` | `wipe 3/-1 -> 0/1` |
| `oldgs`, `view` | `D_Display`'s function-local `oldgamestate`, `viewactivestate`, `menuactivestate`, `borderdrawcount`, hoisted to file scope under `WOOF_IOS`: with `oldgamestate` already `GS_LEVEL`, a session loading straight into a level would skip `R_FillBackScreen` (`d_main.c:321`) | `D_ResetSessionState` | `oldgs -1 -> 0`, `view 0 -> 1` |
| `demoprev` | `demoloop_prev` (`d_main.c`): pointed into the previous session's demo loop, freed by `D_SetupDemoLoop` when it came from a `DEMOLOOP` lump, and read by the first `D_DoAdvanceDemo` (`d_main.c:506`). `demoloop_point`, `demosequence`, `pagename`, `pagetic` go back with it | `D_ResetSessionState` | `demoprev 0 -> 1` |

## The shortlist from the issue

| Variable | Answer |
|---|---|
| `fast_exit` | Real. Reset (`exit`). |
| `current_musicnum` | Harmless: only `S_RestartMusic` reads it, and the early return the issue suspected compares `mus_playing`, not this. The suspicion was right about the symptom and wrong about the variable: `mus_playing` is the bug (`music`). |
| `demo_p`, `deathmatch_p` | Harmless: read only during demo playback/recording, or in deathmatch spawning, and `G_DoPlayDemo`/`P_SetupLevel` reassign them first (rows below). |
| `gameepisode`, `gamemap`, `gameskill` | Harmless: every way into a level sets them first; nothing at the title reads them. (`AM_Start`'s own `lastlevel`/`lastepisode` statics are the real problem with map numbers: #268.) |
| `wipegamestate`, `screen_wipe_internal`, `viewactivestate` | Real. Reset (`wipe`, `view`). The wipe came through `demoloop_prev`, which the issue did not list. |
| `musinfo` | Harmless: `S_Start` clears it at every level start (`s_sound.c:1238`) before the only readers, which run in a level. |
| `rngseed` | Harmless: reseeded from `time(NULL)` by `G_ReloadDefaults` (`g_game.c:4028`) every session, and from the demo header before a demo reads the RNG. |

## Found by reading, not in the diff

The diff sees bytes that differ. A table rewritten with the same values, or a
pointer that keeps pointing at the same place, does not show:

- `mus_playing` (`s_sound.c:83`): reset, above.
- `autoload_paths` (`d_main.c:593`): reset, above; the diff showed only its effect on `next_priority`.
- `hash_table` (`deh_strings.c:34`) and the DEHACKED tables patched in place (`weaponinfo`, ammo, `deh_misc`, `deh_filenames`): #270. Both Freedoom IWADs replace the same strings, so no Freedoom pair can show it.
- `levels` (`p_dirty.c:88`): appended per completed level and never cleared, and matched by episode and map number alone, so a later game's map of the same number could get an earlier game's line and side changes: #268 (it needs a completed level to show).
- The zone (`z_zone.c`): never torn down, so every init-time PU_STATIC allocation used to be orphaned by the next session's. Measured by tracing each block's allocation site and listing session 1's blocks still alive at session 2's checkpoint: 3021 KB (PU_STATIC 1777, PU_CACHE 512, PU_LEVEL 731). The renderer's own tables now free their previous block (`R_InitTextures`, `R_InitFlats`, `R_InitSpriteLumps`, `R_InitColormaps`, `R_InitLightTables`, `R_InitTranMap`, `R_InitSpriteDefs`, `VX_Init`), which brings it to 1004 KB. What is left is mostly the lump cache (PU_STATIC and PU_CACHE lumps and patches, plus the `lumpcache` array). Freeing that in `W_Close` was tried and reverted: session 2 then failed `Z_ChangeTag`/`Z_Free` on a stale lump pointer ("an owner is required for purgable blocks", "freed a pointer without ZONEID"), so every lump holder has to be audited first (#269). PU_LEVEL is not growth: the next level load frees it.
- `AM_Start`'s `lastlevel`/`lastepisode`, `AM_ApplyColors`'s `first_time`: #268.
